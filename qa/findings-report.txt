[HIGH] F-01  Exact-pinned engines + engine-strict made `npm ci` impossible on any other Node/npm patch
  root cause: package.json "engines" were exact version literals and .npmrc set engine-strict=true, so any patch drift hard-failed install — including a NEWER npm (11.13.0 > 11.8.0). frontend/ declared no engines and installed fine, so the two halves of the repo enforced different policies.
  change:
    - package.json engines -> { node: ">=24.22.1 <25", npm: ">=11.8.0" }
    - .npmrc: engine-strict=true commented out, with a comment explaining that the supported toolchain is a range in engines and pinned exactly in .nvmrc/.node-version, and that re-enabling it needs a committed version manager
    - frontend/package.json: declares the same range so both halves agree
  VERIFIED: Plain `npm ci` with NO override: added 204 packages, 0 vulnerabilities, exit 0. Previously EBADENGINE.
  guard: qa/checks/engine-preflight.mjs (UC-01) was rewritten to be range-aware. It FAILS only when a mismatch would actually block install (engine-strict enabled AND toolchain out of range), and warns otherwise — so reintroducing a strict exact pin fails the suite.
  JUDGMENT CALL: Disabling engine-strict is a deliberate trade: the declared floor becomes advisory. Reverse it by uncommenting the directive in .npmrc, but only alongside a committed version manager, or a clean clone becomes uninstallable again on any differing patch.

[MEDIUM] F-02  `npm run test:engines` had an undeclared prerequisite on `vendor:engines` and always failed standalone
  root cause: test:engines consumed vendor/ output produced only by vendor:engines but declared no dependency on it. `npm run check` masked the defect by running `build` earlier in the chain.
  change:
    - package.json: "test:engines": "npm run vendor:engines && node scripts/test-engines.mjs"
  VERIFIED: Deleted vendor/ entirely, then ran `npm run test:engines` standalone with no prior build: 8/8 checks passed, exit 0. Previously MODULE_NOT_FOUND for vendor/meterless/engines/hmem/conformance/runner.js.
  guard: UC-08 in the harness; the curated TestRail case now instructs the tester to delete vendor/ first.

[LOW-MEDIUM] F-03  Strict query-key parsing was applied inconsistently across routes
  root cause: Nine handlers in app/tasks/http.ts enforced an allow-list and rejected duplicate keys with invalid_query, but several read routes never got the same treatment. The events branch validated only the `after` VALUE and used searchParams.get(), which silently returns the first of duplicates.
  change:
    - events route: rejects any key other than `after`, and rejects a repeated `after` (previously ?after=0&after=999999 silently used 0 and returned 52 events)
    - task-read route /api/tasks/:id: rejects any query key
    - /api/capabilities: rejects any query key
    - /api/artifacts/:id (GET): rejects any query key
    - /api/tasks/:id/world: rejects any query key
  scope note: The record named only the events and task-read routes, because those were the only ones the original test probed. Auditing the file showed three more read routes with the same defect, and no caller anywhere in app/, frontend/src, scripts/ or tests/ passes a query to any of them. Fixing only the two named routes would have left the inconsistency the finding describes, so all five were fixed.
  VERIFIED: qa/checks/api-e2e.mjs extended from 30 to 33 checks: 33/33 pass. The task-list route remains an explicit CONTROL proving the policy pre-existed. Verified every caller uses only ?after=<cursor> with a single value, and that ?after=no still returns invalid_cursor (tests/unit/general-http.test.ts:153).
  impact was: Not a security hole — read-only routes behind the localhost + same-origin boundary with server-side identity, and the cursor value was always validated. The cost was a defense-in-depth and debuggability gap: a typo'd or retry-duplicated parameter silently returned unfiltered data from sequence 0 instead of a 400.

[LOW] F-06  Reserved independent-review capacity was never released when the review could no longer run
  record status: UNCONFIRMED hypothesis — it was confirmed with a dedicated probe BEFORE any code was changed, per the no-fix-without-root-cause rule.
  CONFIRMED BY: qa/checks/review-reserve-probe.mjs builds a run with max_model_calls=4 and reserved_model_calls=2 holding a specialist, an EvidenceCritic and a synthesis assignment, and measures how much synthesis can still charge after the critic terminates. Control (critic completed): specialist 2 + synthesis 2 = 4/4 used, 0 stranded. Bug case (critic failed): specialist 2 + synthesis 1 = 3/4 used, synthesis blocked with model_limit while 1 call — exactly floor(reserved/2) — remained claimable by nobody.
  root cause: completedReview recognised only an EvidenceCritic with status === 'completed'. A terminally failed or cancelled critic never satisfied it, so reviewRemaining stayed positive for the rest of the run.
  change:
    - app/tasks/store.ts chargeAttempt: the critics for the current objective revision are collected once; reviewUnavailable is true when at least one critic exists and every one of them is terminal or stale. The reserve is then released to the FINAL SYNTHESIS only (core.manager.synthesis / core.manager.coordinator). Specialist work still may not claim it.
  design: The documented invariant is that 'Required review and synthesis retain capacity before specialist work consumes the budget'. Releasing the reserve to specialists would weaken that and could starve a replacement critic. Releasing it to the finalising assignment removes the stranding without touching the guarantee.
  VERIFIED: Probe re-run: the failed-critic case now matches the control exactly (synthesis 2, usage 4/4, 0 stranded) while the specialist stays capped at 2. Added to the harness as UC-33. Full unit suite still 1328/1328.

[MEDIUM] F-07  A Zetaris publish failure discarded the freshly fetched NASA FIRMS snapshot, and the documented --skip-api retry was unreachable
  found by: Running the real pipeline with a live FIRMS key while Zetaris was down: node --experimental-strip-types app/adapters/zetaris/sources/nasa_firms/fetch_nasa_firms.ts --day-range 1
  root cause: main() fetched and flattened into a staging directory, then called publishToContainer() BEFORE commitCache(), with finally { removeStagingDirectory(staging) }. A failure at the Zetaris publish step therefore deleted the staged data. The script's own --skip-api mode is documented to publish existing cached data, but its guard requires a committed cache that could only exist after a fully successful run, so from a cold start with Zetaris unavailable the recovery path could never be entered.
  observed before: 47 live active-fire records fetched from NASA, publish failed (docker daemon down), then 0 CSV files on disk and --skip-api refused to run.
  change:
    - commitCache(staging, replaceCsv: boolean) became commitCache(staging, names: string[]), keeping its per-entry rollback
    - the raw firms_csv cache is now committed immediately after a successful fetch and flatten, BEFORE the publish step
    - firms_flat is still committed only after a successful publish, so flat still means the last published snapshot
    - on publish failure the script now tells the operator the snapshot was cached and to retry with --skip-api rather than re-fetching
  VERIFIED: Re-ran the real fetch with Zetaris still down: 47 records fetched, publish failed as expected, and 3 CSV files are now retained while firms_flat is correctly left uncommitted. Then --skip-api found the cache and proceeded to the publish step, failing only at Zetaris. The catch-22 is gone. 20/20 related unit tests pass.
  impact: Every fetch attempt while Zetaris was down burned a NASA FIRMS API call and threw away valid satellite data, with no way to stage data for a later publish.
  note: Zetaris itself was never reachable here, so the successful-publish branch remains unverified.

[LOW] F-08  getCsvFiles threw raw ENOENT, defeating the --skip-api guard's actionable message

  root cause: The guard reads if (skipApi && (await getCsvFiles(CSV_DIR)).length === 0) throw ... but getCsvFiles called fs.readdir directly. When the cache directory had never been created the readdir threw first, so the guard could only ever fire for an existing-but-empty directory.

TESTER ERRORS CORRECTED
------------------------------------------------------------------------------

T-01  Harness timeout did not kill the process tree on Windows  [qa/run-usecases.mjs]
  detail: runOne() spawned with shell:true and called child.kill('SIGKILL'), which kills only the shell; npm/node grandchildren survived, held the stdio pipes open, and the 'close' event never fired — so the 300s timeout silently had no effect and the suite stalled. Now uses `taskkill /PID <pid> /T /F` on win32. Confirmed working: UC-26 was terminated at exactly 300s in the next run.

T-02  API test used wrong response accessors  [qa/checks/api-e2e.mjs]
  detail: Error bodies are { error: { code, message } } (app/tasks/http.ts) and successful intake returns HTTP 202 with { task_id, status_url, events_url, reused } — not a flat code/id. The original assertions reported 5 false failures even though the statuses were all correct, and an undefined taskId silently skipped the whole idempotency/events/world/control block. Fixed, and a real reused=true assertion was added.

T-03  STATE_DIR guard drove the wrong entry point  [qa/checks/state-dir-guard.mjs]
  detail: The first version pointed a hostile STATE_DIR at scripts/verify-general.mjs, but that script nests a fresh `general-verification` subdirectory (verify-general.mjs:17-18), so the guard never saw the payload — it reported 4/4 violations against a guard that was actually correct. Rewritten to construct TaskStore directly, with two positive controls: 8/8 pass.

T-04  Two use cases asserted exit 0 on commands that cannot exit 0 unattended  [qa/run-usecases.mjs]
  detail: UC-21 (test:rollback) requires --legacy-executable with a retained pre-LangGraph dist and is a manual cutover tool deliberately excluded from `npm run check`. UC-26 (damage:demo) is a demo server. Both are now marked appropriately — UC-21 optional (WARN), UC-26 replaced by a marker-based probe — so neither pollutes the pass/fail count.

T-05  Prettier false positive and a .cache trap  [.prettierignore, qa/testrail/collect.mjs]
  detail: The initial UC-03 failure was caused entirely by this audit's own unformatted qa/ files; zero pre-existing repo files were unformatted. Generated artifacts are now excluded via qa/*.json and qa/*.txt in .prettierignore while the qa/**/*.mjs sources stay formatted and linted. Separately, the TestRail CLI's default vitest report path was moved out of .cache/ (neither git- nor prettier-ignored, so it would have broken format:check and left an untracked directory) to qa/vitest-results.json.
