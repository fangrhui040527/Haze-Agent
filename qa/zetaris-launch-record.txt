WHY IT WAS POSSIBLE
  An earlier assessment concluded Zetaris could not start. That was correct at the time but incomplete: the Docker daemon was simply not running, and once started, all three required images turned out to be already cached locally from a previous install, so no registry pull or commercial download was needed.

SEQUENCE
  1. Started Docker Desktop; daemon came up as 29.9.2.
  2. Found all three images already cached: zetaris-ndp-driver, zetaris-ndp-api, zetaris-new-ui (2.4.3-v2.4.3.1-hackathon).
  3. Ran the bundle preflight: all required checks passed, with 2 warnings (7GB of 8GB recommended memory; an existing zetaris_pgdata volume).
  4. Rebuilt the root .env from .env.example, RECOVERING POSTGRES_USER/PASSWORD and the admin credentials from the already-running containers rather than inventing new ones - the preflight warns that a different password breaks the query engine against an existing volume.
  5. docker compose up --detach recreated the stale driver; volumes were preserved (no -v).
  6. Moved the Zetaris UI from port 3000 to 3001 because an unrelated project held 3000.
  7. Minted an access token via POST /api/auth/login and stored it with the org id for the Python SQL runner.
  8. Ran the bundle verify script: 9/9 pass, including login and a full ui -> api -> driver -> spark query.

BUG FIXED DURING LAUNCH
  symptom: zetaris-driver-1 exited 127 on restart while api, postgres and ui came up healthy.
  root_cause: The container had been created 29 hours earlier with a bind mount from the repository's OLD location and OLD bundle path (Desktop/Hackathon/Haze-Agent/third_party/zetaris/zetaris-platform/conf/spark-defaults.conf). That path no longer exists: the checkout moved and the bundle now lives at app/adapters/zetaris/zetaris-platform/. Docker created a directory at the missing source and tried to mount it onto a file, so runc failed with 'not a directory'.
  fix: Recreating the container from the current compose.yaml, which points at the path that exists. Restarting the stale container could never have worked.
  verification: driver is now reporting healthy, and the end-to-end query path through Spark passes.

OBSERVATION (not a defect)
------------------------------------------------------------------------------
  The Python SQL runner's REST channel requires a bearer token (ZETARIS_API_KEY) and has no username/password exchange, while the TypeScript client accepts either and mints a token from credentials. That is a deliberate split - REST uses a bearer token, the JDBC channel uses username/password - but it meant a token had to be minted by hand before the registration step could run. Porting the TS login exchange into the Python client would remove that manual step.
