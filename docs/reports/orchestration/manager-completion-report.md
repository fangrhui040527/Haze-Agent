# Manager implementation and verification report

Recorded: 25 October 2026. Scope: [Complete the v3 Manager](../../plans/orchestration/manager-completion-plan.md), implemented as the registered `manager.v4` inside the existing v3 task protocol.

The milestone remains open: the configured real model has not passed the required decision scenarios. Passing scripted scenarios or synthetic PM2.5 verification does not establish Manager quality or successful live PM2.5 retrieval.

The baseline is commit `ce5bf33fbc85097324334a73ffbb297596aec4b0`, using its initial-planning/final-synthesis runtime with the same registered evaluation methods, full-case inputs and resource budgets.

Each case has 90 seconds, 20 model calls, 6 tool attempts, 16 assignments, 64 artifacts, 16,384 input bytes and 1,200 output tokens per model call, reserving 2 model calls. These are matched evaluation budgets, not changes to the application's default profiles. Scripted runs use synthetic decisions and method outputs; live runs use the configured real Manager model with the same synthetic specialist methods. Real-model evaluation therefore tests decisions and supervision, while the separate source probe tests live PM2.5 availability.

Round 1 known-failure and unavailable cases exceeded the unchanged admitted deadline. Their original reports omit final task observations and two provider receipts, leaving the original aggregate at 12 captured calls, 48,353 input tokens and 5,528 output tokens. Read-only inspection of their retained SQLite databases recovered one accepted model receipt per case: 3,877/262 and 3,862/249 input/output tokens. Separate `post_timeout_durable_observation` records bring the captured total to 14 calls and 56,092/6,039 tokens. Both databases retain a saved `wait` and a running run without a final result; the original reports and failed evaluation outcomes remain unchanged. Charged model attempts include provider failures and unknown outcomes; they do not necessarily produce a provider completion. Scripted receipts use null provider/token fields; they are not zero-cost real-model observations. The baseline scripted rejected-review outcome was not a true boolean and is counted as not passing.

Earlier scripted failures exposed overly broad evaluation review requirements, an incorrectly timed peer grant, and a scripted final selection that included reviewer-owned work. The retained failures show these stages rather than replacing them with a later successful trace. The real-model failures exposed invalid reference/action JSON, fabricated UUIDs or hashes, unsupported source selection and waits where a direct supported answer was available. Runtime rejection protects artifacts and authority, but cannot make those decisions succeed.

A [small native-schema probe](../../../.state/manager-evaluation/native-schema-probe.json) succeeded with HTTP 200 and an actual receipt of 43 input and 18 output tokens. The [initial complete Manager schema probe](../../../.state/manager-evaluation/native-manager-schema-probe.json) failed with HTTP 400 because the provider grammar did not implement `propertyNames`. The first full native-schema evaluation consequently failed all 12 cases before producing decisions; no provider token receipts were available. That failed run remains in the results alongside later schema compatibility work. The [normalized complete-schema probe](../../../.state/manager-evaluation/native-manager-schema-normalized-probe.json) then returned HTTP 200 with 24 input and 185 output tokens, establishing provider grammar compatibility while local decision and authority checks remain required.

After schema compatibility changes, the configured model passed direct response, clarification and unavailable-capability blocking. Each used one charged model call and zero specialists, meeting the no-delegation expectations. Known-failure recovery and peer coordination still proposed invalid exact references or participant revisions. For single and parallel specialists, rejected-review repair, conflicting evidence, partial completion, correction and injected-document handling, the provider response could not be accepted as complete; the exact truncation or usage reason was not captured in those historical reports. Those seven cases have no provider token receipts; 6,778 input and 1,307 output tokens cover only the other five cases and cannot establish total provider usage. No failed response is replaced with fixture synthesis.

Evaluator v2 checks unavailable-capability partial/blocked completion. Its correction predicate checks task status and objective revision, and excludes selected old-region findings; it does not establish that a new-region finding is present or that unfinished requirements are fully explained. This lowers the scripted baseline from the earlier 9/12 to 7/12 while the supervised scripted run passes 12/12. These remain checks of control flow and selected outcomes; they do not fully assess prose entailment or scientific validity. The real baseline was rerun with evaluator v2 and passed 5/12, versus 3/12 for the supervised native-schema full run. This matched comparison does not show a quality improvement. The baseline peer case timed out; its durable trace retains one actual model receipt with 1,215 input and 128 output tokens, bringing that full run to 17 charged calls and 18,589/1,398 captured tokens. It remains a failed case.

For example, the real baseline direct case used 1 model call and 1,572 ms; its provider receipt recorded 1,190 input and 60 output tokens. Supervised round 1 direct used 1 call and 3,018 ms with 3,853 input and 204 output tokens. The corresponding single-specialist case failed after 2 calls and 10,595 ms with 8,600 input and 642 output tokens because references/actions did not match the strict schema. The captured results do not support a latency, cost or quality improvement claim over the baseline. A final single-case run from the exact isolated build failed on invented artifact references after one charged call, 4,191 ms, 1,354 input tokens and 353 output tokens. That trace confirms the failure and its retained provider receipt; it does not demonstrate partial-response receipt retention. New adapter and runtime tests verify prospective preservation of failure receipts and partial text, while the seven earlier missing-usage traces remain unknown.

## Remaining requirements and scope

The configured Manager model must pass captured real-model decision scenarios under the strict outcome checks before this milestone can be marked complete. Failures must remain visible alongside any later native-schema or instruction revisions; changing the configured provider/model is not implied by this implementation. Successful live PM2.5 retrieval additionally needs working authorized source credentials and a captured real source trace.

HazeWorld, additional scientific capabilities, World Model acceptance, memory capture, external effects and scheduled monitoring remain outside this milestone. Unrelated workspace changes, including `docs/README.md` and `docs/plans/damage-accountant-plan.md`, are preserved. The source plan's historical status text is not used as evidence of completion and was not rewritten by this report.

## Manager page follow-up — 2026-10-26

The Manager workspace now lives on `/manager/:taskId?`. The dashboard has a **Manager workspace** button, and chat, task reports and Damage accounting link to the exact task's Manager page instead of embedding the panel. The page retains interpretation, plans, assignment revisions, review objections, decision history, inspections and dispatch receipts, plus task controls and clarification. It restores the dashboard's saved task or accepts an explicit task ID; viewing a different task uses separate Manager session storage.

Frontend verification passed 140 tests across 22 files and the TypeScript/production build. Browser checks on explicit fixture state confirmed dashboard navigation, absence of embedded panels in chat and task reports, saved-task validation, direct access, reload and return navigation, and expandable decisions. No browser console errors or horizontal overflow appeared at the existing desktop viewport.
