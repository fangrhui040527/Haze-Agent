# Architecture v0.14 schema catalog and implementation audit

For the complete current named-validator inventory, see [Implemented schema inventory](schema-implementation-status-v014.md). Partially implemented and missing contracts are listed separately in [Remaining schema work](schema-remaining-work-v014.md). This catalog preserves the older audit snapshot described below; newer World Model and domain contracts supersede some of its status findings.

Audited: 26 October 2026. Target: [Haze Agent Architecture v0.14](../Haze_Agent_Architecture_v0.14.pdf), 26 pages. Repository baseline: `ce5bf33`, **including the modified and untracked working-tree files present during this audit**. This is a documentation audit; no application schemas or behavior were changed.

The general task platform has implemented request, task/run, assignment, Manager, artifact, correction, control, event, result and agent-action schemas. PM2.5 and imported damage accounting have concrete domain schemas. The full architecture remains incomplete: accepted/current World Model decisions, external effects, reviewed reusable H-MEM lessons, general monitoring and several scientific work-product families are not implemented in the general task engine.

## How to read the catalog

The PDF specifies logical records and validation responsibilities, rather than a complete set of JSON Schema files. Only the thin control envelope on PDF p.7 prescribes literal field names. Other architecture record names below are **catalog labels inferred from its requirements**, not invented claims that those formal schemas already exist. Code identifiers in backticks are actual implementation names. Page references are PDF page numbers.

Status applies to the schema/contract and its wiring, not scientific validity, production readiness or usefulness:

| Status          | Meaning                                                                                                                                                                             |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Implemented     | Concrete contract and a current consuming implementation exist for the stated scope. Validation may be Zod, SQL or explicit runtime checks; the evidence column distinguishes them. |
| Partial         | An implemented subset exists, but architecture-required content or enforcement is missing.                                                                                          |
| Not implemented | No corresponding implementation was found in the general task path. Related dashboard/vendor code is identified separately where present.                                           |
| Supporting only | A helper, probe, dashboard or vendor contract exists; it does not establish implementation of the general task architecture boundary.                                               |

The active composition is [app/composition.ts](../../../app/composition.ts): Manager, HazeOps, WorkerShield, EvidenceCritic and the additional DamageAccountant; capabilities are `damage-account`, `pm25-evidence-summary`, `episode-investigation` and `evidence-synthesis`. A role does not require its own duplicate task schema: agents share assignment, artifact and action contracts, with domain payloads supplied by capabilities.

## 2. Runtime, lifecycle, messages and checkpoints

The exact p.7 envelope is:

```text
message_id, run_id, assignment_id
objective_revision, assignment_revision
sender, recipient, kind
brief_ref, artifact_refs, control_ref
```

**Partial:** no single schema implements this exact eleven-field envelope. Its responsibilities are distributed across `assignmentSchema`, `taskEventSchema`, `agentActionSchema`, `PeerMessage` and runtime controls. For example, the brief is inline, and peer messages have no `brief_ref` or `control_ref`. Distributed equivalents should not be reported as a literal implementation of the proposed envelope.

## 8. General-engine storage schemas

[TaskStore initialization](../../../app/tasks/store.ts#L260) defines the following SQLite tables. Most payloads are JSON in a `body` column, validated/reloaded by application contracts and explicit transition checks; the SQL schema is not a relational expansion of every payload field.

| Ownership                         | Tables                                                        | Important keys / references                                                                                                   |
| --------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Task/run/assignment               | `tasks`, `runs`, `assignments`, `assignment_history`          | Task principal/workspace; run task_id; assignment task_id/run_id; assignment history primary key `(assignment_id, revision)`. |
| Idempotency/events                | `operations`, `events`                                        | Operations primary key `(scope,key)`, exact fingerprint/receipt; global autoincrement event cursor and indexed task_id.       |
| Immutable content / mutable scope | `artifacts`, `applicability`                                  | Artifact identity; applicability primary key `(task_id,artifact_id,objective_revision)`.                                      |
| Human coordination                | `corrections`, `questions`                                    | Task id plus serialized correction/question record.                                                                           |
| Executed work                     | `attempts`, `actions`                                         | Task/assignment identity; action fingerprint; typed application records described above.                                      |
| Peer collaboration                | `channels`, `channel_history`, `messages`                     | Unique run channel; channel history `(run_id,revision)`; unique message `(channel_id,key)` plus fingerprint.                  |
| Checkpoint references             | `checkpoints`                                                 | Primary key run_id; separate LangGraph SQLite persistence also exists.                                                        |
| Manager coordination              | `manager_state`, `manager_state_history`, `manager_decisions` | Run/task identity; state-history `(run_id,fingerprint)`; decision fingerprint and receipt.                                    |

Storage format marker: `haze.general.sqlite.v1`. Runtime rejects incompatible/unmarked nonempty state directories rather than silently reinterpreting old schemas. These 19 coordination tables are not World Model accepted-state tables.
